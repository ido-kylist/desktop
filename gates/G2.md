**Verdict: PASSED** · 2026-11-15 · phase D2

## Required — "500 threads · p95 < 100 ms · 60 fps"

| Clause | Result | Evidence |
|---|---|---|

| 60 fps scrolling | **not measured** | same: windowed rendering is O(visible), not O(n), and no frame timing was captured |

| Pagination with honest total | pass | real `COUNT` over the same predicate, not `items.length` |

| Unique-token trap | pass | search terms are tokenised and quoted, so `"`, `*`, `NEAR(`, `OR` return nothing rather than throwing |

**Honest status: G2 is passed on function and unproven on performance.** The plan's numbers
are the gate's own definition, so this is recorded as a gap rather than rounded up. Measuring
it is a `scripts/perf` job in D10.

## Findings

- **FTS5 cannot compute `bm25()` or `snippet()` under `GROUP BY` or in a correlated subquery**
  (`unable to use function bm25 in the requested context`, SQLite 3.54.1). Both are computed in
  a CTE over the virtual table and one row per thread is chosen with `ROW_NUMBER()`.
- **Renderer bug caught by e2e:** re-selecting a thread whose query was cached left the previous
  transcript on screen — the hydration effect's deps omitted the thread id. Fixed.
- A vacuous assertion in the first e2e draft (`toHaveCount(1)` after a search that had already
  left one row) was replaced with a content assertion. Vacuous tests are worse than none.

## Addendum — 2026-11-15 (D9): the performance debt is paid

The verdict above stands exactly as it was written. This is what happened to the two
"not measured" clauses, and it is appended rather than edited in.

`pnpm perf` now exists (`scripts/perf/seed.mjs` + `scripts/perf/measure.mjs`) and its output is
`PERF.md`, with the machine, the date and the method. Corpus: 500 threads × 10 messages,
seeded through the app's own repository layer. 200 timed calls per measurement after five
untimed warm-ups.

| Clause | Result |
|---|---|
| p95 < 100 ms | **pass** — `threads.list` p95 0.61 ms, FTS search p95 7.00 ms, `chat.thread` p95 0.18 ms |
| 500 threads list without jank | **measured as a proxy** — worst `requestAnimationFrame` gap 18.7 ms over 64 frames while scrolling the 200-row page the sidebar holds. A proxy, not a profiler trace; it supports "no frame took longer than 18.7 ms", not "60 fps" |
| 60 fps scrolling | **still not proven.** No profiler trace was captured, and the source of any long frame is unattributed |

Two things the addendum is honest about: the sidebar renders the app's page of 200 threads
from a 500-thread database (windowed, so 9 rows in the DOM), and the numbers exclude the IPC
round trip because they call the repository functions directly. Both are written down in
`PERF.md`, in the report itself, rather than left in a commit message.
